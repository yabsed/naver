2010년대에 아이폰이 한국 시장에 출시되면서 한국은 급격하게 모바일 시대로 진입했습니다. 초등학교 때 출시된 카카오톡을 통해서 학창 시절 친구들이 흥분하며 단톡방을 만들던 경험이 기억납니다. 인터넷 서비스가 삶의 중심으로 진입하게 될 것이라는 생각을 했습니다. 중학교 때부터 알고리즘과 프로그래밍을 공부하기 시작했고, 대학교에서 컴퓨터공학부를 공부하기 시작했습니다. 

저의 학부생 시절을 정의하는 활동은 와플스튜디오라는 동아리에서 풀스택 개발자로 활동한 것입니다. 1학년 겨울방학 때 mysql과 django를 이용해 백엔드 서버를 만드는 방법을 배웠습니다. 3학년 겨울방학 때는 React를 이용해서 프런트엔드 서비스를 만드는 법을 배웠습니다. RESTful API와 CRUD를 이용한 간단한 구조를 가지고 프런트엔드와 백엔드가 의사소통하는 개발자들의 업무 방식을 체험했습니다.

# [필수] 팀을 이뤄 협업을 하면서 성과를 이뤘던 경험을 적어주세요. 자신이 어떤 역할로 팀에 기여했고 어떤 교훈을 얻었는지를 포함해 주세요. (단, 학교 팀 과제를 수행한 경우는 제외)

2026년 2월에 와플스튜디오에서 개최된 해커톤에 참여했습니다. 저는 와플스튜디오의 Rookies 세미나에서 배운 React로 막 당근마켓 클론코딩을 한번 해본 상황이었습니다. Rookies를 같이 참여한 친구가 같이 해커톤에 참여해보자고 해서 참여하게 되었습니다. 

저희 팀은 1박 2일 동안 localhost라는 앱을 만들었습니다. 사용자가 동네 매장을 방문해 미션을 인증하면 코인을 받는 앱입니다. 미션은 한산한 시간대 방문, 일정 시간 체류, 영수증 인증, 카메라 보물찾기, 반복 방문 스탬프의 다섯 종류였습니다. 팀원 세 명이 서버와 매장 사장님용 관리자 웹을 맡았고, 저는 사용자가 쓰는 모바일 앱을 혼자 맡았습니다. React Native는 처음이었기 때문에 코드를 쓰는 일은 AI 에이전트에게 맡겼습니다. 대신 저는 앱과 서버가 서로 무엇을 주고받기로 했는지를 확인하는 데 시간을 썼습니다.

문제는 그 약속이 밤새 움직였다는 것입니다. 미션을 인증하는 API가 서버에 처음 올라온 것은 첫날 밤 11시 반이었고, 마감은 다음 날 아침 7시 반이었습니다. 그 여덟 시간 동안 서버는 계속 바뀌었습니다. 새벽 4시 반에는 시간을 판정하는 기준이 한국 시간으로 바뀌었고, 5시에는 사진을 인터넷 주소로 받던 것이 파일로 받는 것으로 바뀌었으며, 7시 직전에는 서버의 주소가 바뀌었습니다. 저는 첫날 저녁에 앱이 서버에 바라는 API를 문서로 정리해 두었지만, 밤사이 실제로 만들어진 서버는 그 문서와 많이 달랐습니다. 솔직히 답답했습니다. 그렇지만 팀원들도 같은 밤에 서버를 처음부터 만들고 있었고, 그들에게 설명서까지 써 달라고 할 수는 없었습니다.

그래서 저는 서버에 묻는 대신 서버를 시험해보기로 했습니다. 일부러 틀린 요청을 보내고, 서버가 돌려주는 실패 안내문을 모았습니다. 이 방법이 가장 잘 통한 곳은 체류 미션입니다. 체류 미션은 매장에 들어갈 때 체크인을 하고 나올 때 체크아웃을 합니다. 서버의 API 설명에는 체크아웃을 하면 성공으로 바뀐다고만 적혀 있었습니다. 그런데 3분 만에 체크아웃을 보내 보니 서버는 "체류 시간 부족 (필요: 20분, 실제: 3분, 남은 시간: 17분)"이라는 실패를 돌려주었고, 그 순간 체크인 기록도 함께 끝나버렸습니다. 서버는 시간이 얼마나 지났는지를 따로 알려주지 않고, 그것을 알려주는 유일한 응답인 체크아웃은 한 번 틀리면 처음부터 다시 해야 한다는 뜻입니다. 그대로 두면 사용자가 종료 버튼을 조금 일찍 누르는 것만으로 20분을 다시 기다려야 합니다. 그래서 앱은 종료 버튼이 눌려도 곧바로 체크아웃을 보내지 않습니다. 먼저 서버에 남아 있는 체크인 시각을 읽어와 앱이 직접 시간을 계산하고, 모자라면 남은 시간만 알려줍니다. 기록을 읽는 것은 몇 번을 해도 아무것도 바꾸지 않기 때문입니다.

스탬프 미션에는 다른 함정이 있었습니다. 제가 써 둔 문서에서는 하루에 도장을 두 번 찍으려 하면 서버가 오류를 돌려주기로 되어 있었습니다. 실제 서버는 오류 대신 도장이 찍혔을 때와 똑같은 모양의 정상 응답에 "오늘은 이미 스탬프를 찍었습니다"라는 안내문 한 줄만 붙여서 돌려주었습니다. 응답이 올 때마다 도장을 하나씩 더하는 앱이었다면 버튼을 누르는 만큼 도장이 늘어났을 것입니다. 그래서 앱은 응답만 보고 숫자를 올리지 않고, 매번 서버의 기록을 다시 읽어서 도장을 셉니다.

서버의 말을 앱의 말로 옮기는 코드는 화면과 떨어진 곳에 모아 두었고, 화면을 그리는 코드는 서버가 어떻게 생겼는지 모르게 했습니다. 새벽 5시에 사진을 보내는 방식이 바뀌었을 때 앱이 30여 분 만에 따라갈 수 있었던 것은 화면을 건드릴 필요가 없었기 때문입니다. 포기한 것도 있습니다. 제가 만들어 둔 '내 활동' 화면은 서버에 제 기록 전체를 한 번에 주는 API가 없어서 새벽 4시 40분쯤에 지웠습니다. 밤을 새우고 있는 팀원에게 새 API를 부탁하는 것보다 제 화면 하나를 지우는 것이 팀에는 더 빠른 길이었습니다.

이 방식은 마감 직후에 시험대에 올랐습니다. 서버를 맡은 팀원들은 마감인 7시 반을 넘겨서까지 AI가 사진을 판정하는 서버의 구조를 통째로 바꾸고 있었습니다. 앱은 코드를 한 줄도 고치지 않고 그대로 동작했습니다. 앱이 믿고 있던 것은 제가 밤새 확인해 둔 약속뿐이었고, 그 약속은 서버의 내부가 바뀌어도 그대로였기 때문입니다. 시연에서는 다섯 미션이 모두 실제 휴대폰에서 동작했고, 저희 팀은 금상을 받았습니다.

이 경험에서 배운 것은 협업에서는 상대가 실제로 어떻게 움직이는지를 확인하는 일이 먼저라는 것입니다. 저는 처음에 제가 쓴 문서대로 서버가 만들어질 것이라고 기대했습니다. 그러나 여러 사람이 동시에 무언가를 만드는 팀에서는 계획과 설명이 항상 실제보다 늦습니다. 그날 밤 제가 한 일은 서버가 이렇게 움직일 것이라는 짐작을 틀린 요청으로 하나씩 공격해보고, 거기서 살아남은 것만 앱이 믿도록 하는 일이었습니다. 덕분에 팀원들은 마감 직전까지 서버를 마음껏 고칠 수 있었고, 앱은 그 변화에 무너지지 않았습니다. 팀에 기여하는 방법에는 직접 많이 만드는 것 말고도, 다른 사람들이 만든 것 사이에서 무엇이 확실한지를 정리해 두는 방법이 있다고 생각합니다.
